# Securo's SimpleFIN provider: the contract this bridge serves

Derived from a line-by-line read of Securo 0.15.0 (`backend/app/providers/simplefin.py`, `services/connection_service.py`, `tasks/sync_tasks.py`) and the public SimpleFIN protocol. Keep the contract test in `test/` aligned with this file.

## Summary

Securo (live image ghcr.io/securo-finance/securo-backend 0.15.0, rev 4a12e9e, on this host as securo-backend/securo-worker/securo-beat, all on the external Docker network traefik_proxy) implements SimpleFIN as a paste-a-token provider whose only host discovery is the pasted Setup Token itself: SIMPLEFIN_API_URL is defined in config.py but never read anywhere in the backend, there is no host/scheme validation, http:// is accepted at both the claim-URL and Access-URL stages, and the bridge base URL is whatever the claim POST returns. The wire protocol Securo actually exercises is: POST <decoded setup token> with Content-Length: 0 (expects 200 + plain-text Access URL with user:pass@ userinfo; 403 = token reused), then GET <access_url>/accounts?version=2 with HTTP Basic auth derived from the userinfo, adding pending=1, account=<id>, start-date/end-date (UTC-midnight epoch seconds, 90-day chunks, end exclusive +1 day) for transaction pulls. From the JSON it reads only errlist[].code/msg, connections[].conn_id/name/org_url|url|sfin_url, accounts[].id/name/currency/balance/conn_id/org{name,domain,url,sfin-url,id}, transactions[].id/amount/posted/transacted_at/description/payee/memo/pending/currency, and holdings[].id/market_value/description/symbol/currency/shares/purchase_price/created/isin/cost_basis; available-balance, balance-date, extra, org_id and the legacy errors array are ignored. Every account is typed "checking" (no inference; the user edits type to credit_card in the UI and Securo then negates SimpleFIN's negative-debt balance), transactions are stored with source="sync", amount=abs(amount), type=debit if amount<0 else credit, date=posted (UTC date) falling back to transacted_at, status=pending iff pending truthy, and dedup is application-level on (account_id, external_id) with a pending-to-posted upgrade only when the id is stable or when a new-id twin matches same date/amount/type/status-differs/description-similarity>=0.7. Sync cadence is a Celery beat task every 3600s that only touches connections with status in (active,error) whose last_sync_at is older than 4h (or null), plus manual POST /api/connections/{id}/sync; each sync does 1 GET for accounts, 1 GET per account for a 14-day rewind window (5 GETs per account for the initial 365-day backfill), 1 GET for holdings when sync_assets is on (default), and 1 extra GET per sync while logo_url is null. All bridge calls use httpx.AsyncClient(timeout=60.0) with no retries and no redirect following. Accounts are auto-created from the payload at connect and at every sync for new ids; there is no manual link/create flow. Actual Budget's sync-server consumes the same bridge but differs materially: it does not send version=2, reads the v1 shapes (accounts[].org.name and the errors array), requires userinfo in the Access URL, requires balance-date, parses balance by stripping the decimal point (so balances must have exactly two decimals), dates pending rows by transacted_at, and its assertUrlAllowed is called with allowPrivateNetwork: true, so an internal bridge works for both if it emits the union of v1 and v2 fields. A bridge at http://israeli-banks-bridge:8080 will work for Securo provided the container joins traefik_proxy (both securo-backend and securo-worker make the HTTP calls) and SIMPLEFIN_ENABLED=true is set for backend and worker; the live stack currently has SIMPLEFIN_ENABLED=false and an empty database (0 bank_connections, 0 transactions, alembic 084).

## Contract

- ENV (backend AND worker processes; beat only schedules): SIMPLEFIN_ENABLED=true is the sole switch (config.py:47, providers/__init__.py:93-95). SIMPLEFIN_API_URL is accepted but unused - set it or not, it changes nothing. The bridge host is fixed entirely by the pasted Setup Token.
- SETUP TOKEN (what the user pastes into Securo's TokenConnectDialog): base64( 'http://israeli-banks-bridge:8080/simplefin/claim/<one-time-id>' ). Standard base64 with '=' padding optional; whitespace/newlines tolerated; decoded string MUST start with http:// or https://. Any scheme/host/port/path is accepted; no allowlist.
- CLAIM ENDPOINT: POST <decoded token URL>. Request from Securo: header Content-Length: 0, Accept: application/json, User-Agent 'Securo/0.1 (+https://usesecuro.com)', no body, no auth. Respond 200 with a text/plain body that is exactly the Access URL, e.g. 'http://<user>:<pass>@israeli-banks-bridge:8080/simplefin' (no trailing slash needed; surrounding quotes/whitespace are stripped). Return 403 on reuse (Securo maps to code 'setup_token_used'; Actual also tolerates 403 at claim). Do NOT redirect (Securo never follows redirects). Userinfo is URL-decoded by Securo (unquote) and by Actual - keep user/pass to [A-Za-z0-9_-] or percent-encode; Actual REQUIRES userinfo to be present.
- ACCESS URL -> ACCOUNTS URL: Securo requests '<access_url rstrip "/">/accounts' with userinfo stripped and sent as HTTP Basic (Authorization: Basic base64(user:pass)). With the example above the path is exactly /simplefin/accounts. The bridge must authenticate the Basic header; if the Access URL has no userinfo Securo sends no Authorization header at all.
- GET /simplefin/accounts query params Securo sends: always version=2; pending=1 on transaction pulls (absent on account-list/holdings/logo pulls); account=<account id> (one per request) on transaction pulls; start-date=<epoch seconds, UTC midnight of window start, inclusive>; end-date=<epoch seconds, UTC midnight of (window end + 1 day), treat as exclusive>. Never sends balances-only. Windows are <= 91 days; initial backfill requests 5 chunks covering today-365..today; incremental requests one chunk covering (last_sync_at.date()-14d)..today. Actual sends start-date, end-date, pending=1 or balances-only=1, repeated account=, and NO version param.
- RESPONSE (200, application/json). Emit the UNION of v1 and v2 shapes so one bridge serves Securo (v2 reader) and Actual (v1 reader): { 'errlist': [ {code: string, msg: string, conn_id?: string, account_id?: string} ], 'errors': [ string ] (v1 mirror of errlist msgs, may be []), 'connections': [ {conn_id: string (<=255, STABLE forever - it becomes bank_connections.external_id and institutions.external_id), name: string (<=255, bank display name), org_id: string, org_url: string (bank website - Securo derives the institution favicon from it and stops the per-sync logo GET), sfin_url: string} ], 'accounts': [ {id: string (<=255, STABLE - accounts.external_id), name: string (<=255, overwritten every sync), conn_id: string (must match a connections[] entry), org: {id: string, name: string, domain: string, url: string, 'sfin-url': string} (v1 fallback; Actual reads org.name), currency: 'ILS' (exactly 3 ASCII letters or Securo forces 'USD'), balance: string with exactly two decimals e.g. '-1234.56' (Securo Decimal; Actual strips the '.' to get cents), 'available-balance': string (optional, ignored by both), 'balance-date': integer epoch seconds (REQUIRED by spec and by Actual; ignored by Securo), transactions: [ ... ], holdings: [ ... ] (optional; omit or [] if not modelled)} ] }.
- TRANSACTION object: { id: string (<=255, STABLE across pending->posted - the single most important property for dedup), posted: integer epoch seconds (0 while pending per spec; Securo dates the row by posted when non-zero, else transacted_at; use a fixed UTC time such as 12:00Z of the booking date so the UTC date never shifts), transacted_at: integer epoch seconds (optional; Actual dates pending rows by it), amount: string, signed, positive = money in / negative = money out (Securo: type='debit' if < 0 else 'credit', stores abs; 2dp), description: string (<=500 after strip; Securo uses description|payee|memo), payee: string (optional; Securo creates/links a Payee entity from it; Actual uses it as payee_name), memo: string (optional; Securo uses only as description fallback), pending: boolean (Securo status='pending' iff truthy; Actual booked=!pending && posted!==0), currency: string (optional; only honoured if exactly 3 letters, else account currency), extra: object (optional, ignored; whole object is persisted verbatim in transactions.raw_data JSON) }.
- HOLDING object (Bridge extension, only read by Securo when sync_assets is on): { id: string (required, stable), market_value: numeric string (required, else the holding is dropped), description: string, symbol: string (<=32, uppercased into assets.ticker), currency: 3-letter code (else account currency), shares: numeric string, purchase_price: numeric string, cost_basis: numeric string, created: epoch seconds (purchase date), isin: string }.
- SIGN / TYPE CONVENTION: Securo types every SimpleFIN account 'checking'. Emit credit-card balances as negative numbers (debt) per SimpleFIN convention; Securo stores them raw until the user edits the account type to credit_card in the UI, after which every sync negates the incoming balance (account_service.py:31-43). For checking accounts emit the real signed balance. Emit card purchases as negative amounts and card repayments as positive.
- ERRORS: put reauth-class failures in errlist as code 'con.auth' or 'gen.auth' with a user-readable msg -> Securo flips the connection to status 'error' and shows a reconnect (re-paste token) banner. Any other code (e.g. 'act.failed', 'con.failed') is logged only and the payload is still consumed. For hard failures use HTTP 401/403 (-> 'error' + reconnect) or 5xx (-> generic 'error'); never 3xx. Do not use 429 expecting a soft skip - Securo has no rate-limit mapping for SimpleFIN.
- REQUEST BUDGET per Securo sync of one connection: 1 GET (accounts, no params but version=2) + 1 GET per account (transactions, incremental) or 5 GETs per account (initial/after reconnect) + 1 GET (holdings, no params) when sync_assets on + 1 GET (logo) while logo_url is null. Syncs happen at most every ~4-5h via beat plus any manual clicks. Each request has a 60s total timeout; the connect request runs all initial pulls synchronously behind traefik/uvicorn, so serve from a pre-scraped cache and answer in well under a second.
- NETWORK: the bridge container must join the external Docker network 'traefik_proxy' (or securo-backend and securo-worker must join the bridge's network) so 'israeli-banks-bridge' resolves from BOTH securo-backend (claim + manual sync) and securo-worker (scheduled sync). Plain http is fine; nothing in Securo enforces TLS or checks the host. Actual's assertUrlAllowed is invoked with allowPrivateNetwork: true so the same internal hostname works for it.
- DEDUP KEYS Securo uses: connection by (workspace, provider, external_id=conn_id); account by (connection_id, external_id=accounts[].id); transaction by (account_id, external_id=transactions[].id) at application level (no DB unique); institution by (connection_id, external_id=conn_id). All ids String(255).
- OPTIONAL: GET /simplefin/info -> {"versions": ["1", "2"]} per spec (neither Securo nor Actual calls it).

## Risks the bridge must design around

- SIMPLEFIN_ENABLED must be true in BOTH securo-backend and securo-worker; if only the backend has it, connecting works but every scheduled sync logs ProviderNotConfiguredError and is skipped (sync_tasks.py:56-59, connection_service.py:1665-1673). The live stack currently has SIMPLEFIN_ENABLED=false for all three processes (.env:70).
- Unstable transaction ids across pending->posted create duplicates: the same-id path only flips status; the new-id path requires identical date, amount, type and description similarity >= 0.7. If the pending row was dated by transacted_at and the posted row by posted on a different day, both rows persist, and Securo never deletes pending rows that disappear from the feed. Emit stable ids and keep the booking date constant.
- Securo never updates amount, date or description of an already-imported id (connection_service.py:1863-1892); a bridge that corrects a transaction after first import must emit it under a new id (which then risks a duplicate). Reversals/deletions upstream are never propagated.
- No DB unique constraint on transactions (account_id, external_id): overlapping manual + scheduled syncs can insert the same id twice (acknowledged in code comment connection_service.py:1855-1861). Keep bridge responses fast and idempotent to shrink that window.
- _cleanup_phantom_duplicates (connection_service.py:1336-1394) deletes a synced transaction that has a transfer-paired sibling with same amount/type within +-1 day and description similarity >= 0.9 - legitimate repeated transfers between two synced accounts on adjacent days (common for Israeli standing orders/card repayments) could be silently deleted.
- All accounts land as type 'checking' and balances are stored raw; a credit card's negative balance will show as an overdrawn checking account until the user edits the type, after which Securo negates the balance and the opening-balance reconciliation re-targets -balance. Communicate this UI step or model cards so their SimpleFIN balance is the debt as a negative number.
- Timezone drift: start-date/end-date are UTC-midnight epochs and 'posted' is converted to a UTC date. Israeli local-time timestamps near midnight (UTC+2/+3) will fall on the previous UTC day and may also be excluded from the 14-day rewind window edge. Emit posted at a fixed midday UTC of the local booking date.
- Redirects are fatal: httpx follow_redirects is off, so an emulator behind a router that 301s (e.g. trailing-slash normalization, http->https upgrade in traefik) breaks both the claim and every /accounts GET.
- SECRET_KEY rotation on the Securo stack invalidates the encrypted Access URL (crypto.py:35-41) -> SessionExpiredError -> status 'expired', which is excluded from automatic sync (status in active,error only) until the user re-pastes a token. The reconnect resets last_sync_at=None, triggering a full 365-day re-pull.
- The connect request performs claim + account list + full 365-day backfill for every account + holdings synchronously inside one HTTP request; with many accounts and a slow bridge this can exceed reverse-proxy timeouts even though each bridge call is capped at 60s. Any failure mid-way raises 400 and nothing is persisted (session rollback), but the setup token has already been consumed - the emulator should tolerate re-claims of a token whose claim never completed, or the user must mint a new one.
- Serving Actual from the same bridge requires the v1 shapes too (org object on accounts, errors array, balance-date, exactly-two-decimal balance strings, userinfo in the Access URL); Securo ignores these extras but Actual crashes or mis-parses without them.
- Currency must be exactly three ASCII letters ('ILS'); anything else is silently replaced by 'USD' at account level and by the account currency at transaction level - a wrong account currency then drives FX stamping of every transaction.
- The public-bridge caps (24 req/day, 90-day windows) do not apply to a self-hosted emulator, but the 90-day chunking still shapes request patterns; a bridge that rejects windows > 90 days is fine, one that rejects overlapping windows is not (Securo deliberately overlaps by 14 days).
- The 'Generate token at SimpleFIN Bridge' button in Securo's dialog always links to bridge.simplefin.org; users must be told to fetch the token from the internal bridge instead (cosmetic only).
- httpx behaviour on 3xx (raise_for_status raising for non-2xx) is stated from httpx 0.28 semantics rather than verified against the library source in the image - marked PLAUSIBLE; the practical guidance (never redirect) holds regardless.

## Open questions (decided for this deployment)

- Is Actual Budget (or its sync-server) actually deployed on this host and expected to share the bridge? Only Securo containers were checked; if Actual is in scope the v1/v2 union payload and two-decimal balance strings become hard requirements rather than nice-to-haves.
- How should the bridge model credit cards - as separate SimpleFIN accounts with negative (debt) balances that the user re-types to credit_card in Securo, or folded into the checking account as transactions? Securo offers no type inference, and the choice determines how card repayments and the opening-balance reconciliation behave.
- What per-connection stability guarantee can the scraper give for transaction ids and booking dates (bank reference numbers vs synthesized hashes)? Securo's dedup depends entirely on it; if the bank changes its own id at posting time, the emulator needs a mapping layer.
- Does the traefik/uvicorn path in front of securo-backend impose a request timeout shorter than the worst-case synchronous connect (claim + 5 chunk GETs per account + holdings)? Not measured.
- Should the emulator honour the version query param (org+errors for missing/1, connections+errlist for 2) or always emit the union? Union is safe for both known consumers; strict versioning matters only if a third, spec-strict client is added.
- Will the operator keep SECRET_KEY stable for the Securo stack? A rotation silently expires every SimpleFIN connection and stops auto-sync until tokens are re-pasted.
- Should the bridge return transactions on the no-parameter GET /accounts?version=2 (Securo's account-list, holdings and logo calls)? Securo ignores them there; returning none saves bandwidth but a spec-strict client might expect a default window.
- How many Israeli-bank accounts/cards will be linked per Setup Token? One token can span several institutions via connections[] and Securo will label the link 'SimpleFIN (N institutions)'; per-bank tokens instead give one Securo connection per bank with independent error/reconnect status.
