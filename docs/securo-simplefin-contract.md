# Securo's SimpleFIN provider: the contract this bridge serves

Derived from Securo 0.15.0, rechecked against the live 0.15.1 backend on 2026-09-07
(`backend/app/providers/simplefin.py`, `services/connection_service.py`, `services/account_service.py`,
`tasks/sync_tasks.py`, `worker.py`) and this bridge's implementation. Keep the contract tests in `test/` aligned
with this file. The behaviors below describe these clients and the bridge, including deliberate extensions to
the public SimpleFIN protocol.

## Summary

Securo claims the URL encoded in a pasted Setup Token, stores the returned Access URL encrypted, and reads the
bridge with HTTP Basic authentication. `SIMPLEFIN_API_URL` is defined but unused by the provider; HTTP and HTTPS
are accepted with no host allowlist. The bridge serves its local ledger, so neither connection nor sync calls
log in to a bank. Backend and worker must both resolve `israeli-banks-bridge` on the single shared external
`traefik_proxy` network. No public router or Authentik exception is needed.

Securo auto-creates accounts, initially all typed `checking`, and deduplicates transactions by account and
external ID. Cards must be retyped to `credit_card`. Initial connection pulls up to 365 days; later syncs rewind
14 days. An hourly task selects connections whose last sync is at least four hours old. The bridge independently
scrapes banks and forwards newly discovered old rows to cover late postings. The wire response retains the
existing union of SimpleFIN v1 and v2 fields consumed by Securo and Actual Budget.

At the 2026-09-07 audit, Securo was 0.15.1, image revision
`6c8c6d2f8dd9f5aa498a6eab74b39077fb089d80`. Backend and worker already had SimpleFIN enabled and ILS supported;
user and workspace currencies were ILS. There were no bridge containers, bank connections, or transactions.
One manual USD checking account existed and must be preserved. Current bank credentials, initial scrape results,
bridge deployment, and a connected Securo account had not been verified. The audit was read-only and made no
bank or sync requests; this is a dated observation, not a claim about subsequent deployment state.

Configuration staged later that day keeps both `hapoalim` and `visaCal` disabled pending current credentials.
The accessible 1Password Connect vault was Home Server, without usable bank login entries; configured item
references are placeholders. Planned scraping is 06:00/18:00 Asia/Jerusalem with at most two login attempts per
company per day, CAL charge-date mode, and pending/synthetic rows disabled. Compose uses internal-only networking,
configuration at `/app/config.json`, data at `/app/data`, and a read-only Connect token. Published-image rollout and
live bank/import verification were pending at note time. A process running with no enabled companies is paused,
not evidence that automatic importing works.

## Contract

- ENV (backend AND worker processes; beat only schedules): SIMPLEFIN_ENABLED=true is the sole switch (config.py:47, providers/__init__.py:93-95). SIMPLEFIN_API_URL is accepted but unused - set it or not, it changes nothing. The bridge host is fixed entirely by the pasted Setup Token.
- SETUP TOKEN (what the user pastes into Securo's TokenConnectDialog): base64( 'http://israeli-banks-bridge:8080/simplefin/claim/<one-time-id>' ). Standard base64 with '=' padding optional; whitespace/newlines tolerated; decoded string MUST start with http:// or https://. Only HTTP/HTTPS schemes are accepted; there is no host/port/path allowlist.
- CLAIM ENDPOINT: POST <decoded token URL>. Request from Securo: header Content-Length: 0, Accept: application/json, User-Agent 'Securo/0.1 (+https://usesecuro.com)', no body, no auth. Respond 200 with a text/plain body that is exactly the Access URL, e.g. 'http://<user>:<pass>@israeli-banks-bridge:8080/simplefin' (no trailing slash needed; surrounding quotes/whitespace are stripped). This bridge permits bounded retries returning the same Access URL through `claimTtlMinutes` and `maxClaims`, even after a successful authenticated GET; reaching either limit closes the claim and yields 403. Unknown claim IDs yield 404. Closing a claim removes its temporary plaintext secret while the hash continues authenticating the consumer. Securo maps claim 403 to `setup_token_used`. Do NOT redirect. Userinfo is URL-decoded by Securo (unquote) and by Actual; Actual requires it to be present.
- ACCESS URL -> ACCOUNTS URL: Securo requests '<access_url rstrip "/">/accounts' with userinfo stripped and sent as HTTP Basic (Authorization: Basic base64(user:pass)). With the example above the path is exactly /simplefin/accounts. The bridge must authenticate the Basic header; if the Access URL has no userinfo Securo sends no Authorization header at all.
- GET /simplefin/accounts query params Securo sends: always version=2; pending=1 on transaction pulls (absent on account-list/holdings/logo pulls); account=<account id> (one per request) on transaction pulls; start-date=<epoch seconds, UTC midnight of window start, inclusive>; end-date=<epoch seconds, UTC midnight of (window end + 1 day), treat as exclusive>. Never sends balances-only. Windows are <= 91 days; initial backfill requests 5 chunks covering today-365..today; incremental requests one chunk covering (last_sync_at.date()-14d)..today. Actual sends start-date, end-date, pending=1 or balances-only=1, repeated account=, and NO version param.
- CLAIM SECRET CLEANUP: the last allowed successful claim returns the Access URL and immediately wipes the stored plaintext copy. Expired plaintext claims are swept at server startup and every 60 seconds, so an abandoned token does not retain plaintext indefinitely. The hashed consumer credential remains usable after claim closure.
- BRIDGE WINDOW EXTENSION: dated requests include a row when its booking date satisfies the lower bound OR `firstSeen` / `postedSeenAt` falls within the requested epoch window. `postedSeenAt` records the first observed pending-to-posted transition, including a hold first seen weeks earlier while pending rows were hidden. The exclusive upper booking-date bound still applies, so this cannot expose future-dated installments early. This delivers late-arriving rows beyond Securo's 14-day rewind without changing their IDs or dates. Repeats across windows are expected and deduplicated by the client. No-window and balances-only responses contain empty transaction arrays. Pending rows require both request `pending=1` and company `includePending=true`; they are omitted once the latest account scrape no longer reports them. Securo does not delete a previously imported pending row just because it disappears from the feed.
- SECURO ACCEPTS LATE ROWS: `SimpleFinProvider.get_transactions` filters account ID and repeated external IDs, but does not trim parsed transaction dates to the requested window. The connection service filters pending status and matches existing rows, without a later requested-date cutoff. An offline fixture against live 0.15.1 accepted a row dated 120 days ago from a request starting 14 days ago; the fixture performed no HTTP requests or database writes. This confirms the bridge's discovery-date extension reaches the import loop.
- RESPONSE (200, application/json). Emit the UNION of v1 and v2 shapes so one bridge serves Securo (v2 reader) and Actual (v1 reader): { 'errlist': [ {code: string, msg: string, conn_id?: string, account_id?: string} ], 'errors': [ string ] (v1 mirror of errlist msgs, may be []), 'connections': [ {conn_id: string (<=255, STABLE forever - it becomes bank_connections.external_id and institutions.external_id), name: string (<=255, bank display name), org_id: string, org_url: string (bank website - Securo derives the institution favicon from it and stops the per-sync logo GET), sfin_url: string} ], 'accounts': [ {id: string (<=255, STABLE - accounts.external_id), name: string (<=255, overwritten every sync), conn_id: string (must match a connections[] entry), org: {id: string, name: string, domain: string, url: string, 'sfin-url': string} (v1 fallback; Actual reads org.name), currency: 'ILS' (exactly 3 ASCII letters or Securo forces 'USD'), balance: string with exactly two decimals e.g. '-1234.56' (Securo Decimal; Actual strips the '.' to get cents), 'available-balance': string (optional, ignored by both), 'balance-date': integer epoch seconds (REQUIRED by spec and by Actual; ignored by Securo), transactions: [ ... ], holdings: [ ... ] (optional; omit or [] if not modelled)} ] }.
- TRANSACTION object: { id: string (<=255, STABLE across pending->posted - the single most important property for dedup), posted: integer epoch seconds (0 while pending per spec; Securo dates the row by posted when non-zero, else transacted_at; use a fixed UTC time such as 12:00Z of the booking date so the UTC date never shifts), transacted_at: integer epoch seconds (optional; Actual dates pending rows by it), amount: string, signed, positive = money in / negative = money out (Securo: type='debit' if < 0 else 'credit', stores abs; 2dp), description: string (<=500 after strip; Securo uses description|payee|memo), payee: string (optional; Securo creates/links a Payee entity from it; Actual uses it as payee_name), memo: string (optional; Securo uses only as description fallback), pending: boolean (Securo status='pending' iff truthy; Actual booked=!pending && posted!==0), currency: string (optional; only honoured if exactly 3 letters, else account currency), extra: object (optional, ignored; whole object is persisted verbatim in transactions.raw_data JSON) }.
- HOLDING object (Bridge extension, only read by Securo when sync_assets is on): { id: string (required, stable), market_value: numeric string (required, else the holding is dropped), description: string, symbol: string (<=32, uppercased into assets.ticker), currency: 3-letter code (else account currency), shares: numeric string, purchase_price: numeric string, cost_basis: numeric string, created: epoch seconds (purchase date), isin: string }.
- SIGN / TYPE CONVENTION: Securo types every SimpleFIN account 'checking'. Emit credit-card balances as negative numbers (debt) per SimpleFIN convention; Securo stores them raw until the user edits the account type to credit_card in the UI, after which every sync negates the incoming balance (account_service.py:31-43). For checking accounts emit the real signed balance. Emit card purchases as negative amounts and card repayments as positive.
- ERRORS: distinguish bridge access from bank login. Invalid/revoked bridge consumer credentials yield HTTP 401, requiring Securo reconnection. This bridge never maps a bank credential, MFA, or CAPTCHA failure to `con.auth`/`gen.auth`: those codes make Securo reject the whole feed and request a new consumer token, which cannot fix bank credentials. A parked company emits sanitized `con.failed`; stale accounts emit `act.failed`; unknown balances emit `act.balance_unavailable` with `0.00`. Securo logs these non-auth warnings and continues consuming cached data. `/healthz` and `bridge status` determine source freshness; successful Securo sync alone does not. Securo treats received `con.auth`/`gen.auth` or HTTP 401/403 as user action required, and 5xx as a generic sync error. Do not use 429 expecting a soft skip: there is no SimpleFIN rate-limit mapping.
- REQUEST BUDGET per Securo sync of one connection: 1 GET (accounts, no params but version=2) + 1 GET per account (transactions, incremental) or 5 GETs per account (initial/after reconnect) + 1 GET (holdings, no params) when sync_assets on + 1 GET (logo) while logo_url is null. Syncs happen at most every ~4-5h via beat plus any manual clicks. Each request has a 60s total timeout; the connect request runs all initial pulls synchronously behind traefik/uvicorn, so serve from a pre-scraped cache and answer in well under a second.
- NETWORK: use only the shared external `traefik_proxy` network, with Compose `default.name: traefik_proxy` and `external: true`. The bridge publishes no host port or Traefik router. BOTH securo-backend (claim + manual sync) and securo-worker (scheduled sync) must resolve `israeli-banks-bridge`. Securo accepts the internal HTTP URL; existing native OIDC protection is unchanged. Actual's `assertUrlAllowed` is invoked with `allowPrivateNetwork: true`, so it can use the internal hostname too.
- IDENTITIES / DEDUP: Securo takes the first `connections[].conn_id` as the bank connection's external ID and first company's name as its institution name. This bridge emits enabled companies in config order even before their first scrape. Keep that order stable. The connect route creates a new bank connection unless `reconnect_connection_id` is provided; connection external ID alone does not prevent duplicate links. Within a link, accounts match `(connection_id, external_id=accounts[].id)`, transactions match `(account_id, external_id=transactions[].id)` at application level (no DB unique constraint), and institutions match `(connection_id, external_id=conn_id)`. IDs are String(255). Separate consumer tokens do not scope or filter companies.
- OPTIONAL: GET /simplefin/info -> {"versions": ["1", "2"]} per spec (neither Securo nor Actual calls it).

## Risks the bridge must design around

- SIMPLEFIN_ENABLED must be true in BOTH securo-backend and securo-worker; if only the backend has it, connecting works but every scheduled sync logs ProviderNotConfiguredError and is skipped. The 2026-09-07 read-only audit verified it true in both processes.
- Unstable transaction ids across pending->posted create duplicates: the same-id path only flips status; the new-id path requires identical date, amount, type and description similarity >= 0.7. If the pending row was dated by transacted_at and the posted row by posted on a different day, both rows persist, and Securo never deletes pending rows that disappear from the feed. Emit stable ids and keep the booking date constant.
- Securo does not overwrite amount, date, or description when syncing an already-imported ID. The bridge freezes those fields per ID and records conflicting same-ID updates as anomalies. Its identity hash also uses transaction fields, so an upstream correction can generate a new ID rather than an anomaly; that can duplicate an economic transaction in Securo. Changing `dateMode` after import can have the same effect. Do not advertise automatic correction/reversal reconciliation; rows disappearing upstream are not automatically deleted.
- No DB unique constraint on transactions (account_id, external_id): overlapping manual + scheduled syncs can insert the same id twice (acknowledged in code comment connection_service.py:1855-1861). Keep bridge responses fast and idempotent to shrink that window.
- _cleanup_phantom_duplicates (connection_service.py:1336-1394) deletes a synced transaction that has a transfer-paired sibling with same amount/type within +-1 day and description similarity >= 0.9 - legitimate repeated transfers between two synced accounts on adjacent days (common for Israeli standing orders/card repayments) could be silently deleted.
- All accounts land as type 'checking' and balances are stored raw; a credit card's negative balance will show as an overdrawn checking account until the user edits the type, after which Securo negates the balance and the opening-balance reconciliation re-targets -balance. Communicate this UI step or model cards so their SimpleFIN balance is the debt as a negative number.
- Some card scrapers do not report a balance. This bridge then emits `0.00` plus `act.balance_unavailable`; that zero is a placeholder, not a verified balance or proof that the card has no debt. Check source data before trusting the account's opening-balance reconciliation.
- Timezone drift: start-date/end-date are UTC-midnight epochs and 'posted' is converted to a UTC date. Israeli local-time timestamps near midnight (UTC+2/+3) will fall on the previous UTC day and may also be excluded from the 14-day rewind window edge. Emit posted at a fixed midday UTC of the local booking date.
- Redirects are fatal: httpx follow_redirects is off, so an emulator behind a router that 301s (e.g. trailing-slash normalization, http->https upgrade in traefik) breaks both the claim and every /accounts GET.
- SECRET_KEY rotation makes the encrypted Access URL unreadable. In 0.15.1, `_access_url` then falls back to an absent plaintext field and `_fetch_accounts` raises `SessionExpiredError`; the connection becomes `expired`, which the scheduler excludes. Reconnect through the existing link so the request includes `reconnect_connection_id`; it saves the credentials, resets `last_sync_at=None`, and returns. The next manual or scheduled sync performs the full 365-day backfill.
- Initial connect performs claim + account list + full 365-day backfill for every account + holdings (when enabled) synchronously in one request. A later failure can roll back the connection after the first authenticated GET has already succeeded. The bridge therefore keeps the claim retryable until its TTL or count limit closes it. Do not close claims merely on the first authenticated GET. A fast local ledger reduces request duration but does not remove this rollback case.
- Serving Actual from the same bridge requires the v1 shapes too (org object on accounts, errors array, balance-date, exactly-two-decimal balance strings, userinfo in the Access URL); Securo ignores these extras but Actual crashes or mis-parses without them.
- Currency must be exactly three ASCII letters ('ILS'); anything else is silently replaced by 'USD' at account level and by the account currency at transaction level - a wrong account currency then drives FX stamping of every transaction.
- Public-bridge request caps do not govern this self-hosted bridge. Securo calculates a nominal chunk end at start plus 90 days, passes end plus one day as the exclusive bound, then starts the next chunk at that bound. A full request therefore spans 91 days; do not reject it at 90 days. The 14-day rewind overlaps previous syncs; the bridge's discovery-date extension can also repeat a row across separate chunks.
- The 'Generate token at SimpleFIN Bridge' button in Securo's dialog always links to bridge.simplefin.org; users must be told to fetch the token from the internal bridge instead (cosmetic only).
- Securo's httpx client does not enable redirect following. A claim response is read as an Access URL; account reads call `raise_for_status()`. The bridge endpoints must answer directly, never through a redirect.

## Deployment choices and remaining verification

- Initial scope is bank and card transactions through one Securo consumer; investment, pension, and provident
  fund sources remain future work. Disable Securo's `sync_assets` for this connection until holdings are supplied.
- Keep cards separate from checking accounts and retype them in Securo. Classify bank-side card repayments as
  transfers to avoid double counting. Synthetic payments stay off; their earliest-row coverage guard does not
  prove a complete statement, and their amount freezes at ledger insertion rather than first delivery.
- CAL's staged `dateMode: "charge"` uses scraper `processedDate` with purchase-date fallback. Validate those
  dates against a real statement before relying on cash-flow reports; leave Securo close/due fields unset until
  validated. The feed sets `posted` and `transacted_at` from the selected booking date and does not expose a
  separate purchase-date field in charge mode. Never invent a due day to work around Securo's cycle calculation.
- Verify current credentials and a successful scrape for each intended company before claiming completion.
  Verify actual account/card coverage, dates, signs, missing-balance flags, and repeated sync behavior afterward.
- Initial real-data connect duration and public reverse-proxy timeout interaction have not been measured.
  Read-only backend/worker metadata reachability checks do not establish a successful financial import.
